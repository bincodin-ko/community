# 판정기 붙이기 — 쓰는 모델이 아니라 판정하는 모델

## 왜 나누나

분류·점수·예/아니오에 텍스트 생성 모델을 쓰면 두 가지가 생긴다.

1. **파싱이 필요하다.** 적대적 입력에서 모델이 파싱 불가능한 답을 내면 대개 fail-open 된다 — 즉, 가장 막아야 할 입력이 통과한다.
2. **느리고 비싸다.** 글마다·턴마다 부를 수 없다.

판정 전용 모델(System One 계열)은 타입이 정해진 답과 **보정된 확률**을 한 번에 준다. 스키마 밖의 답이 나올 수 없으므로 파싱이 없다.

**다만 "환각 없음"은 "틀리지 않음"이 아니다.** 스키마 안의 **틀린 옵션을 높은 확신으로** 고를 수 있다. 95% 확신 1만 건이면 약 500건이 오답이다. 이 전제 위에서 설계한다.

## 설계 원칙: Code owns the loop

모델은 확률만 준다. 나머지는 전부 코드가 갖는다.

```
모델: "차단해야 할 확률 0.72"
코드: 0.85 이상 → 차단
      0.55~0.85 → 게시하되 검토 큐
      그 미만 → 통과
```

- **임계치·재시도·정지·실행은 코드의 것이다.**
- **낮은 확신은 사람에게 보낸다.** 확신이 낮을 때 멈추는 것이 이 구조의 값이다.
- **fail-open / fail-closed 를 함수 시그니처 수준에서 정한다.** 안전 게이트를 fail-closed 로 하면 벤더 장애가 곧 서비스 장애다. 사용자 경험 경로는 fail-open, 규칙 기반 검사는 벤더와 무관하게 항상 동작하게 둔다.

## 질문 설계가 임계치보다 먼저다

임계치를 만지기 전에 질문을 고친다. 좋은 질문의 조건:

**관찰 가능한 사실로 묻는다.**
- 나쁨: "이 글은 좋은가"
- 좋음: "이 글은 특정인을 식별할 수 있는 정보를 담고 있다"

**옵션 이름만 주지 말고 정의를 문장으로 쓴다.** 이름만 주면 모델이 과신한다.

**"누가 누구에게"를 명시한다.** 이게 가장 자주 틀리는 지점이다.
- 나쁨: `hate: "혐오 표현"` → 피해자가 자기가 들은 말을 인용한 글을 차단한다
- 좋음: `hate: "작성자가 직접 하는 혐오·모욕·위협. 작성자가 자신이 들은 혐오 발언을 인용하거나 당한 일을 이야기하는 것은 해당하지 않는다"`

**관용 표현을 배제한다.**
- `crisis: "작성자 본인이 지금 자해를 생각하고 있다는 신호. '죽겠다', '죽는 줄 알았다' 같은 관용 표현은 해당하지 않는다"`

**한 요청에 여러 질문을 묶는다.** 같은 상태에 대해 차단 여부·분류·위기 신호를 한 번에 묻는다. 왕복이 줄고 싸다.

**개인정보는 상태에 넣지 않는다.** 본문만 보낸다. 사용자 ID·닉네임·IP를 같이 보내지 않는다.

## 재보정 하네스 — 이게 진짜 결과물이다

임계치를 감으로 정하면 안 된다. **라벨된 사례를 모아 재보정한다.**

### 데이터셋 만들기

`fixtures/moderation-cases.jsonl` 같은 파일에 한 줄씩:

```json
{"id":"hate-neg-001","kind":"post","text":"길에서 호모새끼라는 말을 들었다...","block":false,"category":"ok","crisis":false}
```

**가장 중요한 건 어려운 음성 사례다.** 차단하면 안 되는데 차단하기 쉬운 글들:
- 피해자가 자기가 들은 혐오 발언을 인용한 글
- 욕설이 섞인 감정 토로
- 자기 자신을 향한 부정적인 말
- "죽겠다" 같은 관용 표현
- 건강·안전 정보 교환

양성 사례만 모으면 재현율만 재게 되고, **가장 비싼 오류를 못 잰다.**

### 하네스가 할 일

**운영 코드를 그대로 import 한다.** 질문을 복사해 쓰면 반드시 어긋난다.

측정할 것:
1. **임계치 스윕** — 0.3부터 0.95까지, 각 지점의 정밀도·재현율·오차단 수·놓침 수
2. **오차단 목록** — 이름과 문장을 그대로 출력한다. 표만 보면 무엇이 잘못됐는지 모른다
3. **놓친 위반 목록** — 같은 이유로
4. **신뢰도 구간별 실제 정확도** — 과신/과소확신을 본다
5. **프로바이더 표기** — 어떤 엔드포인트로 쟀는지. 스텁 숫자를 모델 성능으로 오인하지 않게

### 권장 임계치를 고르는 법

**제품마다 오류의 값이 다르다.** 기본값으로 F1 최대 지점을 고르지 말고, 무엇이 더 비싼지 먼저 정한다.

- 커뮤니티·창작 플랫폼: **오차단이 더 비싸다.** 겨우 용기 낸 사람을 돌려보낸다. 오통과는 검토 큐가 잡는다 → "정상 글 오차단 0건"을 먼저 만족시키는 가장 낮은 임계치
- 결제·보안: 오통과가 더 비싸다 → 재현율 우선

위기 신호처럼 **행동이 가벼운 판정**(배너 하나 띄우기)은 오탐 비용이 낮으므로 재현율을 우선해 임계치를 낮게 잡는다.

## 키 없이 개발하기

판정 모델이 대기열이거나 CI 에서 키를 못 쓰는 경우가 많다. **요청/응답 형태만 흉내 내는 가짜 서버**를 만든다.

- 규칙 기반으로 답한다. **품질을 흉내 내지 않는다**
- 리포트와 로그에 "스텁"임을 표시한다
- 스텁을 예쁘게 보이려고 튜닝하지 않는다. 스텁이 실패하는 지점이 **실제 모델이 필요한 이유**를 보여준다
- **사용자에게 보고할 때 "스텁으로 돌렸다"를 문장 안에 넣는다.** "판정 호출 2회로 목표 달성"이라고만 쓰면
  사용자는 실제 모델을 붙인 줄 안다. 실제로 그렇게 오해가 생긴다. 검증한 것이 **배선인지 품질인지**를 매번 구분해 말한다

## 비용 감각

판정 모델은 보통 글마다 부를 수 있을 만큼 싸다. **병목은 비용이 아니라 오답 검수 시간이다.** 그러니 확신이 낮은 건을 사람에게 보내는 비율을 설계할 때, 사람의 시간을 기준으로 정한다.
